# The stakeholder report — `/security-audit report`

The plan is a work order: Goals, `path:line`, verification commands, written for whoever does the fixing. It cannot answer the only question a client or a delivery lead has, which is *"can we ship, and what are we accepting if we do?"*

This report answers that one. Same findings, different reader — risk stated as consequence rather than mechanism, no line numbers in the body, and the limits of the review promoted to a section instead of a trailing line.

**It is never automatic.** No phase produces it, no gate offers it. It exists only when someone types the subcommand, because a report generated by process rather than by request is the kind nobody reads.

## Where the content comes from

In this order, and never further:

1. **The audit run in this session.** The table is already there; use it.
2. **The newest `docs/security-audit/*-plan.md`** in the audited project, and its embedded `## Findings` table. If the plan has an `## Implementation` log, that log is where status comes from.
3. **Neither exists** — run the audit first, say you are doing so, then report on it.

There is no fourth source. A report is a view of an audit that happened; it never invents findings to fill a template, and a template with two sample findings makes that failure very easy to commit.

## Filling the template

`assets/report-template.html` is the skeleton — 1,200 lines, mostly CSS, with 99 `{{TOKEN}}` placeholders.

**Copy it, then replace into the copy. Do not read the whole file into context to rewrite it.** At ~47 KB it costs roughly 12k tokens to load, nearly all of it stylesheet you will not change. Copy first, then edit the copy with targeted replacements:

```bash
mkdir -p docs/security-audit
cp <skill>/assets/report-template.html docs/security-audit/<YYYY-MM-DD>-<slug>-report.html
grep -o "{{[A-Z0-9_]*}}" docs/security-audit/<YYYY-MM-DD>-<slug>-report.html | sort -u
```

That second command is your worklist. Every token it prints must end up either replaced or deliberately emptied — see the guards below.

The placeholder groups, roughly: document identity (`REPORT_*`, `CLIENT_*`, `AUTHOR_*`, `VENDOR_*`, `DOC_VERSION`, `ENGAGEMENT_REF`), distribution (`DIST_*`), scope (`ASSET_*`, `SCOPE_ONE_LINE`, `COVERAGE_STATEMENT`), method (`CHECK_*`, `TOOL_*`), the exclusions list (`NA_*`), the summary (`VERDICT`, `VERDICT_QUALIFIER`, `EXEC_*`, `COUNT_*`, `PCT_*`, `TOP_*`), and one repeatable finding block (`FINDING_*`, `SEVERITY`, `STATUS`, plus its own fields).

Take the date from the machine — `date +%F` — never from memory. `<slug>` is kebab-case of the audited scope, matching the plan's slug when one exists so the two files sort together.

## The two guards

Both are mandatory, and both are about the same failure: shipping a document that asserts something nobody established.

**1. Delete the sample findings.** The template ships with `ANT-2026-001` and `ANT-2026-007` filled in, plus a `SAMPLE DATA` banner over the chart, so the repeated block can be seen working. A report that keeps them delivers a fabricated critical to a client. Remove both finding blocks and the banner as part of filling, not as a tidy-up afterwards.

**2. Verify before handing over.** One command, and it must come back empty:

```bash
grep -n "SAMPLE\|{{" docs/security-audit/<date>-<slug>-report.html
```

A surviving `{{TOKEN}}` renders literally on the page and reads as sloppiness. A surviving `SAMPLE` badge reads as a real finding. Neither is recoverable once the file is attached to an email.

If a field genuinely has no value, use the template's empty states — `Not assessed`, `Not established` — never a blank. A blank cell in a security report reads as "nothing wrong here", which is the one thing an unfilled field never means.

## Writing for the other reader

**Every sentence traces to a row in the findings table.** The report may not assert an impact the audit did not establish. "Could cost you customers" is only permissible if the audit actually found the path to customer data; otherwise it is invention wearing a suit.

**Business impact is factual consequence, not severity restated.** *"Anyone able to construct a token can act as any user"* is impact. *"This is a critical vulnerability that puts the business at serious risk"* is noise — it tells the reader nothing they can act on and inflates by reflex.

**Keep mechanism out of the body.** No grep patterns, no tool flags, no `path:line` in prose. The affected component field carries the file; the evidence block carries the observation. That is enough — a reader who wants the line number has the plan.

**The `Not assessed` section is the part a stakeholder most needs and least expects.** "We ran a security audit" is heard as "everything was checked". Fill it from the audit's `Not scanned:` line plus anything the scope excluded, one row per area with a reason. The template's two permanent rows — exploitability and runtime/infrastructure — stay in every report regardless of scope, because a source review never covers them. Never leave the list empty.

## Severity and status

Severity carries straight over from the audit table: CRIT → `CRITICAL`, HIGH → `HIGH`, MED → `MEDIUM`, LOW → `LOW`. `INFORMATIONAL` is for observations the audit noted without ranking; do not promote a LOW into it or demote one down.

Status resolves from what exists:

| Situation | Status |
|---|---|
| No plan written | every finding is `OPEN` |
| Plan exists, build not started | `OPEN` |
| Plan's `## Implementation` records the fix | `FIXED` |
| Plan or notes record a decision not to fix | `ACCEPTED` |
| Deliberately scheduled for later | `DEFERRED` |

Never mark something `FIXED` because a plan lists it as a Goal. A Goal is an intention; the `## Implementation` log is the record. That distinction is the whole reason the plan keeps a working log.

## Handing it over

Say where the file is, that it opens in any browser with no network, and that print-to-PDF is the intended way to send it — the print stylesheet handles margins, page breaks, repeated table headers, and a footer carrying `CONFIDENTIAL`, the date, and the version on every page.

Then stop. Publishing it, emailing it, or putting it in front of a client is the human's move, not yours.
